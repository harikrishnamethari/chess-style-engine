## 1. Elevator Pitches

### 30-Second Elevator Pitch
> *"I built Chess Style Engine, an end-to-end full-stack ML system that models and replicates individual human chess playing styles rather than just finding the engine-best move. It uses an AlphaZero-style ResNet policy network conditioned on a continuous 32-dimensional style embedding generated by a recurrent GRU encoder from a player's past games. The model is served via a FastAPI backend over WebSockets with Redis caching and PostgreSQL persistence, connected to an interactive browser frontend featuring live move evaluation and style space interpolation."*

### Two-Minute Deep-Dive Pitch
> *"Most chess AIs focus strictly on superhuman minimax calculation, like Stockfish. My project explores behavioral modeling: predicting the exact moves a specific human would make based on their historical habits.*
>
> *On the ML side, I implemented `ChessStyleNet` in PyTorch. The board is represented as a 14-plane spatial tensor ($8 \times 8$). To personalize play without overfitting to static player IDs, I designed a temporal `HistoryEncoder` using a 2-layer GRU that embeds sequential player statistics—centipawn loss, capture frequency, and game duration—into a continuous 32-dimensional latent vector. This vector is fused into an 8-residual-block CNN torso that outputs over a 4,672-class action space with legal move masking and an auxiliary multi-task blunder detection head.*
>
> *On the software engineering side, I built the backend in FastAPI using SOLID design principles, isolating data ingestion, ORM repositories, and inference singletons. Real-time board interactions run across WebSockets with sub-20ms latency, backed by Redis in-memory caching keyed by FEN and style hashes to prevent redundant neural forward passes. The frontend is built in clean, vanilla JavaScript and HTML5, allowing users to upload PGNs, play against their digital twin, and interpolate between two distinct styles in real time."*

## 2. 20 FastAPI & Backend System Design Interview Questions

1. **Why choose FastAPI over Flask or Django for this ML engine?**
   - *Answer*: FastAPI is natively asynchronous (built on Starlette and ASGI), offering high concurrency for I/O-bound operations and native support for full-duplex WebSockets required for real-time move streaming. It also provides automatic request validation through Pydantic and generates OpenAPI/Swagger documentation out of the box.
2. **How does dependency injection work in your backend?**
   - *Answer*: In `backend/db/session.py`, we define `get_db()`, which yields a SQLAlchemy session and guarantees closure upon response completion. We inject it into route handlers like `upload_pgn` via `db: Session = Depends(get_db)`.
3. **What is the difference between concurrency (`async def`) and parallelism (multiprocessing) in FastAPI?**
   - *Answer*: `async def` handles concurrent I/O operations (like reading uploaded files or WebSocket network frames) cooperatively on an event loop without blocking other threads. CPU-bound tasks (like PyTorch tensor forward passes) run in worker threads or GPU streams.
4. **Why did you implement a WebSocket instead of traditional HTTP polling?**
   - *Answer*: Chess move analysis requires continuous bidirectional communication. HTTP polling incurs heavy HTTP handshake header overhead and latency on every move. WebSockets maintain a single persistent TCP connection, cutting round-trip latency to a few milliseconds.
5. **How does your Redis caching strategy operate?**
   - *Answer*: In `backend/ml/inference.py`, we construct a deterministic cache key by hashing the position FEN string together with the player's history sequence using SHA256 (`cse:<hash>`). If the key exists in Redis, the forward pass is bypassed entirely.
6. **How do you ensure graceful degradation if Redis crashes?**
   - *Answer*: The `InferenceEngine` initializes Redis inside a `try/except` block. If `cache.ping()` fails, `self.cache` is set to `None`, logging a warning and seamlessly falling back to live PyTorch forward passes without throwing a 500 error.
7. **What is the purpose of the Repository pattern in `backend/db/repository.py`?**
   - *Answer*: It separates data access logic from HTTP routing (Single Responsibility Principle). If we migrate from SQLAlchemy to another ORM, or change table schemas, we only modify the repositories without touching route controllers.
8. **How does CORS middleware protect the application?**
   - *Answer*: Configured in `backend/main.py`, `CORSMiddleware` dictates which client domains can interact with the API, preventing unauthorized cross-origin browser requests while allowing the frontend client to query the backend during development.
9. **How are database migrations handled when tables need changes?**
   - *Answer*: While `create_tables()` initializes tables on startup for simplicity, production systems use Alembic to version-control schema migrations without data loss.
10. **Explain how Pydantic Settings handles environment configurations.**
    - *Answer*: `backend/core/config.py` defines `Settings(BaseSettings)`. Pydantic reads from system environment variables or `.env`, automatically performing type coercion (e.g., converting strings to integers or lists) and failing fast on startup if required variables are missing.
11. **Why use an Application Factory (`create_app()`)?**
    - *Answer*: It allows spawning multiple isolated FastAPI app instances with different configurations for unit testing, integration testing, and production deployment.
12. **How do you handle large file uploads without exhausting server RAM?**
    - *Answer*: In `games.py`, we use FastAPI's `UploadFile` which spools files larger than 1MB to temporary disk storage rather than loading the entire file into server memory simultaneously.
13. **How do you prevent SQL injection in your API?**
    - *Answer*: We use SQLAlchemy ORM models and parameterized repository queries (`db.query(User).filter_by(username=username)`), which automatically escape inputs and eliminate raw string concatenation vulnerabilities.
14. **What is Uvicorn and what role does ASGI play?**
    - *Answer*: ASGI (Asynchronous Server Gateway Interface) is the modern Python standard for async web servers. Uvicorn is the lightning-fast ASGI web server that accepts raw HTTP/WebSocket TCP connections and translates them into Python async callables.
15. **How would you scale this backend horizontally to handle 10,000 concurrent players?**
    - *Answer*: Run multiple stateless Uvicorn worker containers behind an Nginx or AWS ALB reverse proxy, scale the PostgreSQL database with read replicas, and use Redis Pub/Sub or a Redis cluster to synchronize WebSocket sessions across server instances.
16. **What is the advantage of using JSON columns in PostgreSQL (`style_embedding`)?**
    - *Answer*: It allows storing arbitrary-length float vectors directly without requiring rigid normalization into 32 separate relational float columns, while remaining queryable.
17. **How do you handle exceptions inside WebSockets?**
    - *Answer*: Inside `backend/api/routes/ws.py`, message handling is wrapped in a `try/except` block that catches JSON decoding errors or invalid FENs and sends structured error frames (`{"type": "error", "message": "..."}`) back to the client instead of abruptly terminating the socket.
18. **Why are static assets served via a separate port/server instead of FastAPI?**
    - *Answer*: Separation of concerns. Python web servers should focus on dynamic compute and ML inference. Static HTML/JS/CSS assets are best served via Nginx, a CDN, or lightweight static file servers for optimal throughput.
19. **How do you monitor backend health in production?**
    - *Answer*: The `/health` endpoint serves as an automated liveness/readiness probe for Docker healthchecks and Kubernetes orchestrators.
20. **What HTTP status codes are used across the endpoints and why?**
    - *Answer*: `200 OK` for successful fetches and uploads, `400 Bad Request` for invalid text encodings, `404 Not Found` for nonexistent users/profiles, and `422 Unprocessable Entity` for syntactically malformed PGN files.

## 3. 20 Machine Learning & PyTorch Interview Questions

1. **Why model move prediction as 4,672-class classification rather than regression or sequence generation?**
   - *Answer*: Chess moves represent discrete transitions on an $8 \times 8$ grid. AlphaZero demonstrated that mapping all possible queen moves, knight jumps, and pawn underpromotions into a fixed discrete action space ($64 \times 73 = 4,672$) allows standard cross-entropy loss to optimize directly over legal move probability distributions.
2. **What is Legal Move Masking and why is it mandatory in game AIs?**
   - *Answer*: Neural networks output unconstrained real-valued logits across all 4,672 classes. Without masking, the model might assign highest probability to an illegal move. By setting illegal logits to $-\infty$ (or $-10^9$) before applying Softmax, illegal moves receive exactly zero probability.
3. **Why did you use a GRU instead of an LSTM or Transformer for the `HistoryEncoder`?**
   - *Answer*: The input history is relatively short (sequence length of 10 games $\times$ 3 features). A GRU has fewer parameters than an LSTM (no separate cell state), trains significantly faster, requires less data to avoid overfitting, and is computationally cheaper than self-attention for tiny sequences.
4. **How does the model handle Black's perspective?**
   - *Answer*: Through canonical board flipping: when Black is to move, the $8 \times 8$ board is vertically inverted, and White/Black piece planes are swapped. This allows the neural network to learn a single unified set of weights that always plays from the perspective of the moving player.
5. **What is the difference between one-hot player conditioning and your HistoryEncoder approach?**
   - *Answer*: An `nn.Embedding(player_id)` lookup assigns a static vector to known players. When a new user signs up, the model has no embedding for them and fails. The `HistoryEncoder` takes *behavioral stats* (centipawn loss, capture frequency) as input, allowing it to generalize to completely unseen players (zero-shot style transfer).
6. **Explain the multi-task learning objective in this network.**
   - *Answer*: The total loss is $\mathcal{L} = \mathcal{L}_{\text{policy}} + 0.25 \cdot \mathcal{L}_{\text{blunder}}$. The shared ResNet representations must simultaneously predict the next human move (policy) and evaluate whether the move is tactically sound (blunder risk). The auxiliary task acts as a regularizer, preventing the network from overfitting to rare suboptimal human moves.
7. **What is the role of Residual Blocks in the board torso?**
   - *Answer*: Residual skip connections ($\mathbf{x} + \mathcal{F}(\mathbf{x})$) solve the vanishing gradient problem in deep networks, allowing gradients to flow unimpeded directly through the identity shortcuts during backpropagation.
8. **Why is Batch Normalization included after each convolution?**
   - *Answer*: It stabilizes training by zero-centering and scaling activations across mini-batches, mitigating internal covariate shift and allowing the use of higher learning rates.
9. **How does Style Interpolation work mathematically?**
   - *Answer*: Given style vectors $\mathbf{v}_A, \mathbf{v}_B \in \mathbb{R}^{32}$, a blended style vector is computed as $\mathbf{v}_{\text{blend}} = \alpha \mathbf{v}_A + (1 - \alpha) \mathbf{v}_B$ where $\alpha \in [0, 1]$. Because the latent space is continuous (bounded by $\tanh$), feeding $\mathbf{v}_{\text{blend}}$ smoothly shifts the output move probabilities between Player A's and Player B's tendencies.
10. **What is Top-$k$ Accuracy and why is it preferred over Top-1 for human behavioral modeling?**
    - *Answer*: In any given chess position, there are often 3 to 5 equally viable moves. Top-1 accuracy only rewards matching the single historical move played in that game, whereas Top-3 and Top-5 accuracy measure whether the model recognized the human's candidate move pool.
11. **How do you measure whether style conditioning actually changes model behavior?**
    - *Answer*: By computing the Kullback-Leibler (KL) divergence between predicted move distributions $P_A(m)$ and $P_B(m)$ on identical board states. If $D_{\text{KL}} > 0$, the style vector is proven to have an active causal impact on decision-making.
12. **What optimizer is used and why?**
    - *Answer*: AdamW with cosine learning rate scheduling. AdamW fixes the flawed weight decay implementation of standard Adam, ensuring effective $L_2$ regularization that prevents convolution filters from growing excessively large.
13. **Why do we use Gradient Clipping during training?**
    - *Answer*: Recurrent architectures (like the GRU `HistoryEncoder`) can suffer from exploding gradients when unrolled over sequences. Clipping gradients at `max_norm=1.0` ensures numerical stability.
14. **How are draws and endgame states handled in training data?**
    - *Answer*: Positions where the game has ended (checkmate or stalemate) have no legal follow-up moves and are filtered out of the training dataset to prevent NaN loss calculations.
15. **What constitutes data leakage in chess move prediction and how is it prevented?**
    - *Answer*: Data leakage occurs if positions from the same game appear in both the training and validation sets, as adjacent plies share near-identical board states. Splitting must be performed at the **game level**, never at the individual position level.
16. **Why are piece channels separated into 12 planes rather than a single plane with piece integer IDs (e.g. Pawn=1, Knight=2)?**
    - *Answer*: Integer IDs impose an artificial, false ordinal relationship (implying a Queen with ID 5 is "five times" a Pawn with ID 1). Binary one-hot planes allow convolutional filters to activate independently on piece spatial distributions.
17. **What is the spatial dimension preserved by the ResNet torso?**
    - *Answer*: It retains the native $8 \times 8$ board dimensions throughout all 8 residual blocks using padding=1, ensuring that square coordinates and diagonal/orthogonal relationships are preserved without loss from pooling.
18. **How does Global Average Pooling (GAP) benefit the blunder head?**
    - *Answer*: GAP condenses the $64 \times 8 \times 8$ spatial feature maps into a 64-dimensional vector by averaging across squares. This dramatically reduces parameter count compared to fully-connected flattening and acts as a strong structural regularizer.
19. **What is the total parameter count of ChessStyleNet?**
    - *Answer*: Approximately 544,000 parameters. This lightweight footprint is intentionally engineered so that the model can run sub-20ms inference on standard CPUs without requiring an expensive dedicated GPU in production.
20. **Can this model hallucinate chess rules?**
    - *Answer*: The neural network can assign non-zero logits to illegal moves, but the system architecture guarantees that the *user never sees an illegal move* because the `InferenceEngine` enforces a strict mathematical legal move mask prior to returning results.

## 4. 15 Project-Specific Technical Decisions & Tradeoffs

1. **Why use vanilla HTML/CSS/JS instead of React, Next.js, or Angular?**
   - *Answer*: To eliminate build step overhead (no Webpack/Node runtime dependencies), reduce client-side bundle size to zero, ensure maximum browser compatibility, and keep the focus purely on backend architecture and ML modeling.
2. **Why not just download the entire monthly Lichess database dump for training?**
   - *Answer*: Monthly Lichess dumps exceed 30GB compressed ($>200\text{GB}$ uncompressed), which is impractical for fast personal training. We created a targeted Lichess API ingestion pipeline that streams personal games directly via username in under 15 seconds.
3. **Why is the model loaded as a singleton in `backend/ml/inference.py`?**
   - *Answer*: Instantiating a deep learning model loads weights into memory and allocates CUDA/CPU buffers. Loading it once at application startup ensures sub-millisecond response times for subsequent requests and avoids memory leaks.
4. **Why store style embeddings as JSON in PostgreSQL?**
   - *Answer*: A 32-dimensional float array is compact ($\sim 250$ bytes). Storing it as a JSON/JSONB column provides flexibility without requiring specialized vector database extensions like pgvector for small-scale deployments.
5. **How did you organize the codebase to satisfy SOLID principles?**
   - *Answer*: We separated the monolithic scripts into distinct single-responsibility packages: `src/core/` for board encoding, `src/ml/` for PyTorch networks, `src/training/` for optimization loops, and `backend/db/` for database repositories.
6. **What is the purpose of backward compatibility stubs like `src/model.py`?**
   - *Answer*: When restructuring an active project to adhere to clean architecture, moving files can break existing scripts or notebooks. Legacy stubs re-export symbols from the new package paths, preventing import errors.
7. **Why was Chart.js selected for the similarity visualization?**
   - *Answer*: It is an ultra-lightweight canvas-based visualization library that runs directly in the browser, ideal for rendering dynamic 2D scatter plots of player embeddings.
8. **How do you handle model inference if no trained checkpoint exists?**
   - *Answer*: The `InferenceEngine` checks `os.path.exists(settings.model_path)`. If absent, it logs a clear warning and initializes `ChessStyleNet` with random weights, allowing the entire full-stack application to boot and pass integration tests without failing.
9. **How does the system ensure reproducible training runs?**
   - *Answer*: By setting manual random seeds across PyTorch (`torch.manual_seed`), NumPy (`np.random.seed`), and Python's `random` module in the training scripts.
10. **Why are centipawn loss and capture rate used as the core style metrics?**
    - *Answer*: Centipawn loss quantifies positional precision (tactical strength), while capture rate quantifies aggression and willingness to complicate positions. Together, they provide orthogonal signals that distinguish wild tactical players from calm positional grinders.
11. **Why is `chessboard.js` coupled with `chess.js` on the frontend?**
    - *Answer*: `chessboard.js` is strictly a visual rendering widget with no knowledge of chess rules. `chess.js` acts as the client-side game engine that validates legal piece movements, handles castling/en-passant rules, and formats standard FEN strings.
12. **How does the WebSocket server handle client disconnections?**
    - *Answer*: The connection loop is wrapped in a `try...except WebSocketDisconnect` block, ensuring that when a player closes their browser tab, connection resources and session histories are cleanly deallocated.
13. **Why did you use Docker Compose for local development?**
    - *Answer*: It defines PostgreSQL, Redis, and FastAPI in a single declarative `docker-compose.yml`, ensuring that developers can spin up the entire multi-service environment with one command (`docker-compose up`) without manual database setup.
14. **How are unit tests structured?**
    - *Answer*: In `tests/`, we isolate components: `test_board_encoding.py` verifies tensor dimensions without PyTorch, `test_model.py` checks forward pass shapes and gradient flow, and `test_pgn_parser.py` validates metadata extraction.
15. **What is the most technically challenging bug you encountered and resolved?**
    - *Answer*: When parsing PGNs, `chess.pgn.read_game()` is lenient and returns an empty Game object on invalid text rather than `None`. We solved this by verifying that the parsed game contains actual moves (`game.end().ply() > 0`) before accepting it, preventing empty training samples.
